# kcapk

`kcapk` is a small manifest-driven Android application builder.

It keeps one general Android build path while allowing each project to define
its own frontend and, when needed, its own native integration.

The builder is a single POSIX shell script. No Gradle or Android Studio project
is required for the normal build flow.

## Effective architecture

- AndroidBridge is common kcapk infrastructure.
- NativeBridge is project-specific.
- kclibs are build-time native dependencies only.
- Native `.so` files ship with the APK/AAB and are not runtime-updated.
- Web assets may continue to update independently.
- Project JNI/native integration belongs in `projects/NAME/native/`.

## Layout

```text
kcapk/
|-- scripts/
|   |-- build.sh
|   |-- install.sh
|   `-- uninstall.sh
|-- repo/
|   |-- build.sh
|   |-- assets/
|   `-- projects/NAME/
|       |-- config.json
|       |-- manifest.json
|       |-- assets/
|       |-- native/          # project-specific native integration when present
|       `-- app/             # generated build tree; do not edit
`-- dist/
    `-- NAME/
        |-- manifest.json
        |-- NAME.apk
        `-- www/
```

## Build

From `repo/`:

```sh
./build.sh NAME
```

Thin operator helpers are available under `scripts/`.

The general builder remains responsible for Android mechanics such as:

- SDK/build-tool setup;
- generated Android project files;
- resources and icons;
- WebView shell;
- common AndroidBridge support;
- web asset staging/provisioning;
- project-native compilation;
- APK/AAB packaging;
- signing;
- publication.

## Project contract

A project has a small declarative contract.

Example `manifest.json`:

```json
{
  "kclib": ["redp2p"],
  "start": "www/index.html"
}
```

`start` selects the application start document.

`kclib` selects build-time kclib dependencies. It does not define a JavaScript
API or automatically expose a dependency through NativeBridge.

## Kclib dependency model

For a dependency `NAME`, the builder resolves the canonical kclib distribution
package under:

```text
KCLIB_DIST_DIR/NAME.c/
```

The canonical Android inputs are:

```text
KCLIB_DIST_DIR/NAME.c/source.zip
KCLIB_DIST_DIR/NAME.c/aarch64/android/libNAME.so
KCLIB_DIST_DIR/NAME.c/armv7/android/libNAME.so
```

`source.zip` supplies the public header used to compile the project-native
integration. The expected public header is:

```text
src/libNAME.h
```

The builder is responsible for extracting source.zip into build staging,
preparing include paths, selecting the Android ABI binaries, and packaging the
native libraries.

Projects should not manually copy kclib headers or `.so` files when the builder
can derive them from the canonical distribution.

## Native release model

Native libraries are part of the APK/AAB release.

They are not intended to update independently at runtime.

If a native dependency changes incompatibly, rebuild the affected application
with the matching headers, JNI/native integration, and `.so` files.

This keeps compatibility local to the application instead of imposing a common
ABI across unrelated libraries.

## AndroidBridge and NativeBridge

The application shell has two separate bridge concepts.

AndroidBridge is common kcapk infrastructure for Android-specific capabilities.

NativeBridge is project-specific and exposes only the native application
surface that the project intentionally defines.

Conceptually:

```text
WebView / JavaScript
    |
    +-- AndroidBridge
    |
    +-- NativeBridge
          |
          +-- project JNI/native code
                  |
                  +-- kclib dependencies
                  +-- custom native code
```

Declaring a kclib dependency does not automatically expose it through
NativeBridge.

There is no generic native runner or common kclib ABI.

## Web assets

Web assets remain separate from native dependencies.

The existing provisioning model may continue to provide:

- embedded first-run assets;
- remote web asset updates;
- SHA-256 verification;
- offline fallback;
- splash progress and warnings.

Native `.so` files must not use the same independent runtime update mechanism.

## Generated tree

`projects/NAME/app/` is generated by the builder.

Do not edit it by hand.

Changes to generated Java, AndroidManifest.xml, native packaging, or other
generated behavior belong in `repo/build.sh` or the canonical project source
that feeds it.

## Development rule

Automate deterministic build mechanics.

Keep semantic application integration explicit.

If behavior can be derived reliably from `manifest.json` and the canonical
kclib dist layout, it belongs in the builder.

If behavior depends on what a specific application wants to expose or do, it
belongs in that project.
