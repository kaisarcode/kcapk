# kcapk

`kcapk` is a small manifest-driven Android application builder.

It keeps one general Android build path while allowing each project to define
its own frontend and, when needed, its own native integration.

The builder is a single POSIX shell script. No Gradle or Android Studio project
is required for the normal build flow.

## Effective architecture

- AndroidBridge is common kcapk infrastructure.
- NativeBridge is generated common kcapk infrastructure.
- libabi is an implicit mandatory build-time native dependency.
- manifest-selected kclibs are optional build-time dependencies exposed by NativeBridge.
- Native `.so` files ship with the APK/AAB and are not runtime-updated.
- Web assets may continue to update independently.
- Project JNI/native integration belongs in `projects/NAME/native/`.

## Layout

```text
kcapk/
|-- scripts/
|   |-- build.sh
|   |-- install.sh
|   `-- uninstall.sh
|-- repo/
|   |-- build.sh
|   |-- assets/
|   `-- projects/NAME/
|       |-- config.json
|       |-- manifest.json
|       |-- assets/
|       |-- native/          # project-specific native integration when present
|       `-- app/             # generated build tree; do not edit
`-- dist/
    `-- NAME/
        |-- manifest.json
        |-- NAME.apk
        `-- www/
```

## Build

From `repo/`:

```sh
./build.sh NAME
```

Thin operator helpers are available under `scripts/`.

The general builder remains responsible for Android mechanics such as:

- SDK/build-tool setup;
- generated Android project files;
- resources and icons;
- WebView shell;
- common AndroidBridge support;
- web asset staging/provisioning;
- project-native compilation;
- APK/AAB packaging;
- signing;
- publication.

## Project contract

A project has a small declarative contract.

Example `manifest.json`:

```json
{
  "kclib": ["redp2p"],
  "start": "www/index.html"
}
```

`start` selects the application start document.

`kclib` selects optional application kclibs. Do not list `abi`: the builder
always includes it. Selected kclibs are automatically available through the
generated NativeBridge, while abi itself is not exposed to JavaScript.

## Kclib dependency model

The effective native dependency set is `abi` plus every `NAME` in
`manifest.json:kclib`. The builder resolves each canonical distribution package
under:

```text
KCLIB_DIST_DIR/NAME.c/
```

The canonical Android inputs are:

```text
KCLIB_DIST_DIR/NAME.c/source.zip
KCLIB_DIST_DIR/NAME.c/aarch64/android/libNAME.so
KCLIB_DIST_DIR/NAME.c/armv7/android/libNAME.so
```

`source.zip` supplies bridge and project-native headers. Optional kclibs use:

```text
src/libNAME.h
```

libabi uses `src/abi.h`. The builder extracts sources into build staging,
generates the common Java/JNI bridge, selects Android ABI binaries, and packages
the native libraries. Every APK/AAB contains `libabi.so` and only the
manifest-selected optional `libNAME.so` files in addition to the common bridge.

Projects should not manually copy kclib headers or `.so` files when the builder
can derive them from the canonical distribution.

## Native release model

Native libraries are part of the APK/AAB release.

They are not intended to update independently at runtime.

If a native dependency changes incompatibly, rebuild the affected application
with matching libabi metadata and `.so` files.

## AndroidBridge and NativeBridge

The application shell has two separate bridge concepts.

AndroidBridge is common kcapk infrastructure for Android-specific capabilities.

NativeBridge is generated by `build.sh`. It maintains the existing trusted
WebView capability gate, accepts only a manifest-selected library and a known
libabi function, dynamically resolves the selected packaged symbol, invokes it,
and returns a JSON result or explicit error. It never accepts paths or arbitrary
process symbols from JavaScript.

Conceptually:

```text
WebView / JavaScript
    |
    +-- AndroidBridge
    |
    +-- NativeBridge
          |
          +-- generated Java bridge
                  |
                  +-- common native dispatcher
                          |
                          +-- libabi metadata
                          +-- dlsym on selected libNAME.so
```

For example, trusted JavaScript can call
`NativeBridge.callNative(token, "redp2p", "redp2p_version", "[]")` without a
per-function Java/JNI mapping. Functions requiring arguments or unsupported
return categories are rejected explicitly by the current common dispatcher.

## Web assets

Web assets remain separate from native dependencies.

The existing provisioning model may continue to provide:

- embedded first-run assets;
- remote web asset updates;
- SHA-256 verification;
- offline fallback;
- splash progress and warnings.

Native `.so` files must not use the same independent runtime update mechanism.

## Generated tree

`projects/NAME/app/` is generated by the builder.

Do not edit it by hand.

Changes to generated Java, JNI dispatch, AndroidManifest.xml, native packaging,
or other generated behavior belong in `repo/build.sh`.

## Development rule

Automate deterministic build mechanics.

If behavior can be derived reliably from `manifest.json` and the canonical
kclib dist layout, it belongs in the builder.

`projects/NAME/native/bridge.c` remains available for project-specific native
behavior, but ordinary selected kclib calls belong to the generated bridge.
